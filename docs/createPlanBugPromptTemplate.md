## Bug Work Item Rules

A `### Bug:` item under a Feature has the following supported fields — use only these:

| Markdown field | AzDo reference name | Notes |
|---|---|---|
| `{tags}` | System.Tags | camelCase, comma-separated |
| `{Story Points}` | Microsoft.VSTS.Scheduling.StoryPoints | 1 SP = 1 human working day |
| `{Priority}` | Microsoft.VSTS.Common.Priority | 1–4, 1 = highest |
| `{Description}` | System.Description | Multi-line; include persona layout + sub-headers |
| `{Repro Steps}` | Microsoft.VSTS.TCM.ReproSteps | Multi-line numbered list |
| `{Extra Information}` | Custom.ExtraInformation | Links, notes, workarounds |

**Do NOT use** `{Acceptance Criteria}` or `{Acceptance Tests}` — these fields are not defined for Bug work items in this AzDo project.

### Bug description rules
- Write the description using the same persona layout as stories:
  ```
  **As a** [persona]
  **I want** [correct behaviour]
  **So that** [impact]
  ```
- After the persona block, use level-4 headers (`####`) for sub-sections such as:
  - `#### Steps to Reproduce`
  - `#### Expected Behaviour`
  - `#### Actual Behaviour`
  - `#### Environment`

### Repro Steps field
- Use `{Repro Steps}` as a dedicated field (not inside Description) for the numbered reproduction steps.
- This maps to `Microsoft.VSTS.TCM.ReproSteps` in AzDo.

### Story Points for bugs
- Estimate as human working days needed to investigate + fix + verify.
- Use the same scale as stories: 0.125, 0.25, 0.5, 0.75, 1, 2, 3, 5 …

## Output Requirements

- If the feature already has a plan file in `docs/plans/`, append the new `### Bug:` block(s) to that file.
- Otherwise create a new file named `docs/plans/plan-tbd-bug{BugTitle}.md` (camelCase title, no spaces) containing the epic/feature header and the new bug(s).
  The `tbd` placeholder is replaced with the bug's work item ID once the plan is persisted via `NewAzDoHierarchyFromMarkdown.ps1`.
  Example: `plan-tbd-bugAsteriskFieldSyntax.md` → renamed to `plan-2705-bugAsteriskFieldSyntax.md` after creation.
- Follow `example-hierarchy.md` for structure and formatting.
- Do NOT include a `{WorkItemId}` for new bugs.
- **Every non-blank line in the output file MUST end with two trailing spaces** (`  `) — see the "Markdown line break rule" in the Plan Creation Rules above.
